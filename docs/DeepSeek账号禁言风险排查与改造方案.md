# DeepSeek 账号禁言风险排查与改造方案

排查日期：2026-10-12（Asia/Shanghai）

最初排查阶段只读取代码、相关 Codex 会话执行记录和公开资料，并运行无浏览器、无真实联网的认证失败模拟。随后按用户确认的请求控制方案修改了插件代码。整个改造验证使用内存模拟和隔离浏览器中的本地页面，没有使用用户账号请求 DeepSeek、登录或发送真实消息。

## 已实施的改造（2026-10-12）

- 移除启动、定时和打开会话时的主动全量扫描/预先校验。接收原生历史及删除响应，只有新增消息或分支变化时针对对应会话补读，失败不自动循环重试。
- 页面请求观察脚本在 document_start 的 MAIN world 加载，优先接收原生账号信息。插件不调用 users/current 或登录接口，不搜索 token，不进行 Cookie 回退重试。登录失效只通报并停止主动请求；其他标签页的旧账号信息不能恢复队列。
- 归类、记忆整理、压缩及接续全局串行。失败任务保留记录并跳过；原始草稿、原有记忆保留，重试需用户主动操作。接续等待回复结束，超时关闭插件创建的任务页，再启动下一个任务。
- 限流冷却覆盖主动历史读取、自动清理及新任务，状态保存在本地，可跨后台重载。暂停覆盖新任务、后台补读及清理，正常聊天和本地项目操作继续。
- 设置按钮显示红点，设置页面顶部显示持续红色提醒和未完成任务入口。账号限制不自动探测解除；用户确认原生聊天恢复后可手动恢复插件任务。
- 保留自动化会话最近十个的功能；空闲且列表变化时才进行必要清理，失败保留提醒且不循环尝试。

这些改造减少不合理请求，不代表已证实禁言原因，也不能保证平台不会限制必要的网页自动化调用。以下排查记录保留为当时的风险依据和方案背景。

## 判断与边界

优先怀疑插件的主动历史扫描、网页后台模型调用，以及登录/限制响应后的持续请求。这些路径是代码中可确认的风险；尚无服务器处罚原因或禁言前的请求日志，不能把它们写成此次禁言的确定原因。

没有发现插件清除登录 token、Cookie、localStorage 或主动退出账号的代码。多次需要重新登录可能与服务端会话失效、限制处理或其他会话变化有关；仅凭现象不能判断因果方向。

当前账号提示禁言至 2026-10-15 20:52。恢复使用的条件以 DeepSeek 的实际提示和官方处理结果为准。

## 按排查优先级排序的风险

### 1. 打开和刷新页面会重扫全部已登记会话

位置：`core/content/workbench.js:671`、`:1329`、`:1340`；`core/background/workbench.js:833`。

- 扫描队列来自所有未标记删除的本地会话，包括普通和自动化会话，不仅是当前查看的会话。
- 扫描启动时执行，页面可见期间每 5 分钟再执行；时间同步发现变化也会触发扫描。
- 启动认领主要防止同时扫描；扫描完成后释放，缺少跨标签页持久化的最近成功扫描时间与扫描预算。
- 当前历史读取间隔为 1 秒。大量历史、频繁刷新、扩展重载会放大请求量；这一间隔是插件自己选择的参数，没有证据表明它是网页端官方允许的阈值。

示例估算：若登记了 100 个会话，一次全量扫描会尝试约 100 个历史读取操作；认证回退和重试会增加实际请求次数。这是代码行为估算，不是此次账号的实测数量。

### 2. 自动记忆任务通过网页持续创建并发送会话

位置：`core/background/workbench.js:633`、`:729`；`core/content/workbench.js:864`；`core/background/session-memory.js:144`、`:243`。

- `automationPaused` 默认是 false；后台任务会开 DeepSeek 标签页、写入提示词并触发原生发送。
- 队列最多同时执行两个插件任务；个人/项目记忆任务有顺序限制，但归类任务仍可能与记忆任务并行。
- 项目旧会话分别产生个人和项目整理任务，通常是两次模型输入；还有归类、压缩和接续任务。
- 较早会话变化后，会重放该记忆范围后续会话。一次修改可能引出多次重新整理。
- 没有统一的网页模型调用间隔、累计调用预算或账号限制状态。单个任务失败后，其他可执行任务仍能继续。

这条路径需要优先调整。降低 GET 频率并不能消除后台网页生成请求。

### 3. 登录失效未触发账号级停止

位置：`core/content/workbench.js:1279`；`core/page/page-network.js:228`、`:267`；`core/logic/history-core.js:20`。

- 账号识别最多检查 20 次，每次失败后等待 500 ms。
- 页面钩子碰到 `40003 / INVALID_TOKEN` 会去掉 Bearer 再用 Cookie 尝试一次。失效信息没有作为明确停止原因传给账号识别循环。
- 历史读取也有认证回退；上层全量扫描会对普通错误再尝试一次，并继续处理其他会话。
- 当前打开会话的定时读取只在成功后更新时间。持续失败时，1.5 秒 UI 定时循环仍可能反复进入读取路径，不能把它理解成失败后也固定每 20 秒才尝试。

本轮离线模拟将所有账号接口响应设为 `40003 / INVALID_TOKEN`，确认一次 `getAccount()` 会进行 **20 次账号检查、40 次模拟接口调用**。模拟使用固定虚构凭据和内存 Response，没有浏览器、真实账号或真实 HTTP 请求。

重新登录之前应该先停止插件请求，而不是让失效凭据继续被使用。

### 4. 限流保护只覆盖部分读取路径

位置：`core/background/workbench.js:852`、`:23`；`core/page/page-network.js:285`；`core/content/workbench.js:864`。

- 历史读取的冷却是后台内存 Map；重载扩展会丢失该状态。
- 账号检查、会话列表主动读取、删除和模型生成不共用这一冷却。
- 会话列表读取在任意 HTTP 失败后都可能用 Cookie 回退，包括 HTTP 429。认证回退不应该用于处理限流。
- 自动化等待结果时捕获历史错误后继续等待；没有把认证失败、限流或禁言升级成停止全账号自动化的信号。
- `network-applied` 在请求体改写完成时产生，不能作为服务端已接受生成请求的证明。

### 5. 暂停任务队列不会停止扫描和自动删除

位置：`core/content/workbench.js:1344`；`core/background/workbench.js:1244`。

网页每分钟触发自动化会话清理，可能产生账号检查和远端删除请求。该路径不检查 `automationPaused`；历史同步也不依赖这个开关。因此当前“暂停队列”不能作为完整的网络停止开关。

### 6. 历史内容会作为新输入再次经过服务端

位置：`core/background/session-memory.js:231`。

完整用户和助手内容会拼入记忆整理提示词。已有历史在重新整理时成为新的模型输入。自动化频率之外，历史内容是否触发内容处理也是一个待查方向；本轮未读取用户聊天正文，没有证据指向某类内容。

## 公开资料能支持到什么程度

DeepSeek [用户协议](https://cdn.deepseek.com/policies/zh-CN/deepseek-terms-of-use.html) 第 3.5 节列出了不合理负载、自动工具抓取等限制，第 8.1 节列出了限制账号功能等处理措施。协议没有给出可据以保证插件安全的网页 GET / 生成请求频率。不能根据“请求间隔一秒”推导它符合官方网页使用条件，也不能据此认定此次处罚就是某个条款触发。

公开社区有“反复退出登录，重新登录后发现账号被限制”的[第一手反馈](https://www.reddit.com/r/DeepSeek/comments/1wz3l3x/i_keep_getting_logged_out_of_deepseek_3rd_time/)。它只能说明类似现象存在，不能证明插件导致这些案例。未检索到用户提及的具体小红书笔记原文，不能确认其插件类型和请求方式。

官方 [API 错误码](https://api-docs.deepseek.com/zh-cn/quick_start/error_codes/) 和限速文档描述的是开放平台，不能直接当作网页端的风控阈值。自动模型任务可以设计为使用 [官方 API](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)，其费用按输入输出 token 计量；它同样有使用规则，接入目的应是采用官方自动化渠道。

## 修改方案

### P0：先提供完整停止机制

1. 增加账号级持久化状态，记录认证失效、限流冷却、账号限制、发送结果待确认等停止原因。扩展重载和重新登录不能自动清除停止状态。
2. 遇到明确 401、403、`INVALID_TOKEN`、禁言提示时，停止该账号的主动历史读取、账号检查、会话列表读取、模型生成和远端删除；已发送的任务保留待核对状态。
3. 429 处理遵循服务端 `Retry-After`，没有提示时使用保守冷却；阻止 Cookie 回退、循环切换凭据和连续新建任务。冷却参数只能降低频率，不能保证账号不会受限。
4. 默认暂停网页自动创建/发送会话和远端自动删除；既有保存的数据、处理记录、任务结果保留。已有账号迁移时也应进入暂停状态，仅修改默认值不能覆盖此前保存的启用设置。
5. 将“暂停自动化”明确覆盖所有插件主动请求。恢复时显示待处理数量，由用户主动选择恢复；限制状态下不得排空历史队列。

### P1：降低额外网页请求，保留项目体验

1. 取消启动全量扫描、5 分钟全量扫描和空闲期间的当前会话轮询。优先使用原生页面已发生的列表、历史和消息响应，不额外发相同请求。
2. 以内容版本和原生变化信号更新本地记录。主动补同步只处理明确选定的范围，并由唯一账号级调度器认领。
3. 停止遍历本地存储猜测 token；插件不负责恢复网站登录。认证失效等待用户通过原生页面处理。
4. 自动化会话展示仍可只显示最近 10 条；远端删除改为用户明确发起的原生操作，避免持续后台写操作。
5. 项目树、折叠、归类管理、记忆管理和导入导出继续使用本地数据。提示词可以先形成用户可查看的草稿，再通过正常网页操作发送。

### P2：自动记忆改用正式模型渠道

恢复账号并确认可用权限后，将归类、个人/项目记忆整理和压缩改为后台调用官方 API 或本地模型，取消使用网页辅助标签页完成这些任务的方式。API 凭据独立配置，不从网页登录信息推断，不纳入记忆导出或诊断日志。

保留现有队列、内容指纹、失败保存、人工固定条目和原子提交；在同一会话处理同类数据时减少重复输入。较早会话发生变化后，保留一致性重放能力，但给出预计范围、调用数量和费用，避免无提示地启动大批任务。

不使用换账号、改 IP、伪装点击或随机延时来规避平台限制。采用正式渠道和减少请求是产品架构调整，不保证账号处罚会因此自动解除。

## 诊断和验证

- 增加本地请求元数据日志：时间、来源、接口路径、任务类型、HTTP / 业务错误码、耗时和成功/失败；不保存 token、Cookie、请求头或聊天正文。
- 单独统计人工操作触发与插件自动触发的请求。账号状态变化同步通知所有插件标签页。
- 默认测试只使用临时配置和本地模拟；网络测试环境阻止访问真实 DeepSeek 域名。旧 `.live-profile` 不用于自动回归。
- 真实站点测试需要显式开启，并先确保所有主动联网任务都已停止；修正旧 UI 测试查找错误后台路径的问题。仅“测试不主动点发送”不足以保证扩展加载后没有后台请求。
- 验证明确认证失败只尝试一次并停止全部任务；429 不进行凭据回退；重载不丢冷却；多标签页不会重复扫描；暂停后不会删除或发消息；发送结果不明时不自动重发。
- 本轮没有服务器处罚日志和禁言前的完整请求记录，无法给出准确触发请求、次数或内容。

## 当前建议

先停用扩展，关闭它打开的自动化标签页，保留本地数据，暂不继续发送或反复登录验证。通过官方“联系我们”入口说明重登和禁言的时间线，询问触发原因及恢复条件；官方协议提供的对话服务邮箱是 `service@deepseek.com`。

推荐先实施 P0 和 P1；需要真正无人值守的记忆 agent 时实施 P2。只调整网页轮询间隔，无法解决自动化渠道和认证失效继续请求的问题。
